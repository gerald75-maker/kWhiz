# kWhiz — Leçons

[2026-07-28] | Le bouton Menu était signalé comme ne se fermant pas au second clic, mais la source et le bundle local contenaient déjà le bon comportement d’ouverture/fermeture ; ajouter un nouveau correctif aurait dupliqué une logique saine, tandis qu’une ancienne PWA mise en cache reste une explication plausible | Avant de corriger un bug d’interaction rapporté, vérifier la source, le bundle construit et le mécanisme de mise à jour ; si le comportement est déjà correct localement, renforcer la validation et investiguer la version réellement déployée plutôt que modifier la logique sans cause reproduite.

[2026-07-28] | Les textes visibles ne se trouvent pas uniquement dans `index.html` : certaines chaînes sont générées dans les vues JavaScript, proviennent de `public/tarifs.json`, du manifeste PWA ou de pseudo-éléments CSS | Pour tout audit éditorial, inventorier séparément les textes statiques, dynamiques, accessibles (`aria-label`, `alt`, `title`), les données affichées et les contenus CSS avant de corriger ; préserver les identifiants et les constantes qui participent à la logique.

[2026-06-22] | Remplacement de couleurs par `sed`/regex en aveugle peut corrompre des valeurs hex qui partagent un préfixe (ex. `#22c55e` est préfixe de `#22c55e22`, une couleur 8 chiffres avec alpha utilisée dans `.planner-badge`) | Avant tout remplacement en masse d'une couleur hex, grep d'abord toutes les occurrences de cette chaîne (y compris en sous-chaîne) et les couleurs de marque opérateur qui pourraient coïncider, puis traiter les cas ambigus avec des Edit ciblés plutôt qu'un remplacement global.

[2026-06-22] | Une maquette/preview approuvée peut impliquer une restructuration de rendu (ex. tableau → grille de cartes) qui n'est pas explicitement demandée et peut être disproportionnée par rapport au reste du changement | Avant d'implémenter fidèlement un détail visuel de preview, vérifier s'il nécessite un nouveau chemin de rendu (JS) ou si l'objectif peut être atteint en CSS sur la structure existante ; privilégier la seconde option et le signaler clairement à l'utilisateur plutôt que de décider en silence.

[2026-06-22] | `#tab-profile` est à la fois un `.tab-content` (caché via `display:none` par défaut) et la cible d'un layout CSS Grid desktop — un sélecteur `#tab-profile { display:grid }` sans le qualifier par `.active` aurait une spécificité supérieure à `.tab-content.active` et resterait visible même onglet inactif | Quand on ajoute des styles desktop sur un élément déjà contrôlé par une classe d'état (`.active`, `.open`, etc.), toujours qualifier le sélecteur avec cette classe d'état pour ne pas casser la logique d'affichage existante.

[2026-06-22] | Avant de bump une version dans package.json, vérifier la valeur réelle actuelle (et son backup) plutôt que de se fier à un résumé/mémoire de conversation précédente | Confirmé : la valeur mémorisée (2.0.2) était fausse, la vraie était 2.0.6. Toujours relire le fichier avant d'agir sur une valeur numérique sensible.

[2026-06-22] | Lors de la normalisation vers le design system canonique partagé (kWhiz/Wattway/Wattlog), le brief de référence supposait que `--bg-card` (#13263D) et `--text-secondary` (#A8B3C7) du brief original n'avaient pas encore été appliqués littéralement — en réalité le CSS shippé utilisait déjà `#1e293b` et `#94a3b8` (probablement ajustés en cours d'implémentation initiale, divergence jamais documentée). Seul `--bg-main-solid`/`--bg-main` (#071426) restait à corriger vers #0F172A. De même, la "carte gagnante #18364F" mentionnée dans le brief n'existe dans aucun fichier de code réel (seulement dans preview/*.html, des maquettes statiques jamais committées comme code de prod) : `.profile-best-card` utilise `background: var(--bg-card)` + halo `rgba(22,199,132,...)`, donc aucune 3e couleur de fond à gérer. | Avant tout remplacement de couleur "censé" exister selon un brief/une doc, grep d'abord la valeur dans le code réel pour vérifier si elle est encore présente telle quelle — un brief ou une doc de design peut décrire un état antérieur ou une maquette jamais reportée fidèlement dans le code final.

[2026-06-22] | `npm run build` échoue dans l'environnement sandbox Linux du Cowork (`Cannot find module @rollup/rollup-linux-arm64-gnu`) car `node_modules` ne contient que le binaire natif `@rollup/rollup-darwin-arm64` (installé depuis le Mac de Gérald) | Ne pas interpréter un échec de build comme une régression de code sans vérifier d'abord s'il s'agit d'une incompatibilité de plateforme (binaire natif manquant pour l'OS du sandbox) — dans ce cas, valider via accolades CSS équilibrées + `node --check` + JSON.parse, et signaler que le vrai build doit être relancé sur la machine de Gérald (macOS) où le binaire natif correct est présent.

[2026-06-22] | Bug rapporté par Gérald (PWA installée sur écran d'accueil, mode standalone) : pendant le scroll, le slider de conso en haut se fait partiellement masquer et la bottom-nav semble se décaler. Cause confirmée pour le slider : `.bottom-nav` avait déjà `padding-bottom: env(safe-area-inset-bottom)` mais `.sticky-top` n'avait pas l'équivalent `padding-top: env(safe-area-inset-top)` — au repos le `<h1>` au-dessus masquait le trou, mais dès que `.sticky-top` se colle à `top:0` pendant le scroll il passe sous la status bar (mode `black-translucent`). Pour la bottom-nav, aucune cause CSS trouvée (pas de transform sur un ancêtre qui casserait le containing block de `position:fixed`, pas de règle dupliquée) — confirmé par Gérald que ce n'est pas du Safari en onglet (donc pas le bug classique de barre d'outils Safari qui se rétracte) ; correctif appliqué à titre de mitigation standard (bug WebKit connu : `position:fixed` + `backdrop-filter` peut "traîner" pendant le scroll inertiel sans calque GPU dédié) — `transform: translateZ(0)` + `will-change: transform` ajoutés sur `.bottom-nav` pour forcer la promotion de calque. | Un correctif basé sur l'absence de cause identifiable dans le code est une mitigation, pas une certitude de root cause — le dire explicitement à Gérald et lui demander de vérifier sur l'appareil réel après le prochain déploiement plutôt que de marquer la tâche "résolue" sans preuve.
